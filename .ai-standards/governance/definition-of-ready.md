# Definition of Ready Standard

## 1. Objetivo

Este documento define os critérios mínimos exigidos pelo framework de Product Delivery para considerar uma iniciativa, funcionalidade ou User Story "Ready for Development" (Pronta para Desenvolvimento).

A centralização da Definition of Ready (DoR) visa garantir que o time de desenvolvimento receba requisitos consistentes e com redução drástica de incertezas de negócio, evitando retrabalho.

## 2. Gate Aplicável

Os critérios deste documento aplicam-se no momento do **Feature Definition Approval Gate** (para Features), do **Ready for Development Gate** (para itens individuais como User Stories) e do **Backlog Readiness Gate** (para conjuntos de itens).

## 3. Critérios Mínimos (DoR)

Para que um artefato de produto (como uma User Story) seja considerado "Pronto", ele deve possuir:

1. **Objetivo compreensível:** O problema ou necessidade que está sendo resolvido está claro para a equipe técnica.
2. **Valor identificado:** Está claro por que essa entrega importa para o produto ou usuário final.
3. **Escopo definido:** Limites claros do que será construído e do que NÃO será construído foram estabelecidos.
4. **Critérios de Aceitação (Acceptance Criteria):** Estão claros, definidos de forma objetiva, verificáveis e cobrem cenários relevantes (positivos, negativos e limites).
5. **Dependências conhecidas:** Identificação de qualquer dependência externa, de infraestrutura, de regras de outro sistema ou de outras histórias que precisem ser resolvidas previamente.
6. **Perguntas críticas resolvidas:** Nenhuma incerteza de negócio que possa afetar severamente a arquitetura ou o fluxo do usuário deve estar aberta. 
7. **Rastreabilidade estabelecida:** O artefato possui vínculos documentados (IDs, links) para suas origens (Discovery, PRD, Requirements) para facilitar análise de impacto.
8. **Ausência de ambiguidades críticas:** Regras e termos vagos (como "rápido", "fácil", "suporta muitos") foram quantificados ou devidamente esclarecidos.
9. **Coerência Geral:** Os requisitos da história não entram em conflito lógico com as definições consolidadas no PRD e nos Requisitos Funcionais/Não Funcionais da iniciativa.

## 4. Extensões de Projeto

A Definition of Ready acima reflete os critérios de prontidão do ponto de vista do **produto (Product Delivery)**.

Equipes ou projetos podem (e devem) adicionar critérios técnicos operacionais específicos de sua realidade (ex: "protótipo Figma anexado", "arquitetura revisada", "estimativa preenchida no Jira"), mantendo esta base como os requisitos mínimos e inegociáveis.
